# Google connection and travel estimates

Enable Gmail API and Google Calendar API in a Google Cloud project. Configure Google Auth Platform consent for the test account and create a **Web application** OAuth client. Set the server's client ID, client secret, and exact callback URL locally; never commit these values or OAuth tokens. The callback handler must validate a random, single use OAuth `state` before calling `exchangeCode`.

For this local server, set `GOOGLE_REDIRECT_URI=http://localhost:3333/oauth/google/callback` and register that exact redirect in the OAuth client. This keeps Google sign in independent of the temporary phone webhook tunnel. `PUBLIC_BASE_URL` remains the public address for phone and sensor webhooks. If `GOOGLE_REDIRECT_URI` is omitted, the server uses the public base URL plus `/oauth/google/callback`.

In Connections, select an account and choose **Connect account**. Repeat for additional accounts. Enro verifies the consenting account through Gmail's profile endpoint before saving credentials, rejects a different account when a specific email was selected, and stores each account separately in ignored `.data/google-accounts.json`. Reconnecting one account preserves the others. Calendar events and email invitations keep their source account and distinct IDs; email source links select the corresponding Gmail account. A sync reads all connected accounts and leaves existing source events untouched if any account request fails. The connection indicator reflects locally available tokens; a successful sync establishes actual provider access.

Private `.data/preferences.json` stores the home landmark, preferred travel modes, preparation/arrival buffers, and suggested Google accounts. The authenticated `/api/preferences` endpoint updates these settings. The planner preloads them without putting personal settings in tracked source files. Driving, walking, and transit remain individually selectable for each plan.

Enro requests only `calendar.events.readonly` and `gmail.readonly`. It reads primary calendar events during the next seven days, expands recurring instances, preserves the source timezone, and excludes all day, cancelled, self declined, past, and unlocated events. Tentative events remain marked tentative. Refresh tokens support background reads after consent; authorization can still expire or be revoked, so failed refresh requires reconnecting.

Email import searches a bounded set of ten recent invitation, appointment, reservation, event, or ICS messages. It recursively decodes plain text and calendar attachments, preferring plain text over HTML. **Structured one off ICS invitations are normalized** when they contain an unambiguous UTC or IANA timezone start, title, and location. Attendance requires one explicit confirmation before a plan can be created. Later revisions of that invitation retain attendance; cancellations disarm plans. Recurring, floating, all day, ambiguous DST, or incomplete invitations stay in the source review workflow. Other email text requires manual confirmation of event details. The received timestamp is never used as the event time. Imports are bounded to ten matching messages, so an invitation absent from a later import disarms its plan conservatively; absence alone does not establish cancellation.

Enable Google Maps Routes API and configure a server only API key restricted to that API. Maps billing must be enabled. Route requests fail visibly when credentials are absent, billing/API access is unavailable, or no route exists; there is no guessed travel duration.

For UCSD source events, the known room codes `WLH`, `COA`, and `PCYNH` resolve to Warren Lecture Hall, Coalition, and Pepper Canyon Hall at UC San Diego. The event retains its original room, while the review screen shows the building used for routing. Other locations are sent as entered. Explicit online locations and Zoom, Google Meet, or Teams links remain visible but cannot create a travel plan. These aliases come from [UCSD's classroom directory](https://mathweb.ucsd.edu/~gptesler/assigningseats.html); routes end at the building, so allow extra time to reach the room.

- **Drive:** Google ignores `arrivalTime` for driving. Enro first queries traffic near the desired arrival, then makes up to two refinements at `arrival minus estimated duration`. It retains the longest estimate across these requests. This is a conservative approximation, not an exact arrival time solver or a guarantee against future traffic changes. Up to three billable Routes calls are made per driving estimate.
- **Transit:** Enro requests `arrivalTime` and calculates the departure from the first scheduled transit leg minus the preceding walking time. The effective duration includes the gap between the itinerary and the requested arrival deadline, preventing a later departure that misses an infrequent service. Missing itinerary details produce an error.
- **Walk:** The returned walking duration is used without traffic preferences.

The caller should request arrival at **event start minus arrival buffer**, then subtract returned duration to get leave time, then subtract preparation time to get wake time. A future refresh requires recalculating the plan rather than reusing an old route indefinitely.

The event review screen reuses only matching Google plans with estimates fetched within 15 minutes. Changes to travel mode, event time/place, preparation, arrival buffer, or vehicle access time require a new calculation. Plans are saved with calls off.

Provider tests use injected fake HTTP responses only. They establish request, parsing, filtering, account separation, and scheduling behavior, not live account connectivity or real route availability. Live connection results are recorded separately in `.hackathon/SERVICES.md`.
